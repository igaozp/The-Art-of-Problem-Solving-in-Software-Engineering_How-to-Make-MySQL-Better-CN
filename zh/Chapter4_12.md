## 4.12 软件测试

### 4.12.1 测试对 MySQL 开发人员的重要性

对 MySQL 开发者而言，测试与开发不可分。内核复杂，外部测试人员难掌握细节，多只能黑盒测。正因复杂，更需要足够用例压住回归成本。开发者应会用用例有效验证自己的改动。

### 4.12.2 平衡测试用例和开发效率

不是每个问题都值得写用例：有时写用例比修代码还贵。例如基于 Paxos 的通信路径，长期缺少专项用例，主要靠开发者大量手工测。

原则应是：成本合理就补用例，成本过高就暂缓，把关系摆平才能提高整体效率。

需要注意，组复制现有用例偏松，重构后回归很难做；用例又多又松时，大量时间耗在区分“用例本身有问题”还是“重构引入问题”。

### 4.12.3 确保测试环境的一致性

结果会随环境波动，环境一致才能谈公平。SSD 显著缩短 MySQL I/O 等待，但若不监控 SSD 性能衰减，结果会偏离预期；`fstrim -a` 等手段可减轻磨损/降速干扰。

Linux 页缓存也会让间隔很久的两次测试不可比，故应缩短测试间隔，并重复首轮测试评估波动；波动大时结果可能无效。

本书多用 BenchmarkSQL 或 SysBench。BenchmarkSQL 会随时间堆数据，为保证可比性，一般在重建库后开测，便于重复。

### 4.12.4 如何高效测试？

最有效的是用真实在线流量，但对数据库风险高。更稳妥的是把流量复制到专用测试环境。

Oracle Database Replay 用生产负载测变更，能以较低开销捕获工作负载并在测试系统回放，保留并发与负载特征。缺数据依赖同步时，负载往往跑不真，覆盖差、压力不足，很多问题测不出来；基于数据依赖的同步才能更接近真实 [34]。

MySQL 侧常见做法：拉起接近生产的测试主节点（可从从库脱机改造集群），再把在线请求复制过去。越接近生产，结论越可信。复制手段很多，本书推荐开源 [TCPCopy](https://enhancedformysql.github.io/animation/how_tcpcopy_works.html) [65]；实践中已用它解决过大量线上问题，也为代理类增强提供基础 [66]。测集群时，用 TCPCopy 把在线请求打到测试系统，可检验改动是否达到预期（性能、稳健性等）。

### 4.12.5 测试是关于发现问题还是验证问题？

测试既要验证已知点，也要主动发现新问题。先确认行为符合预期，再把重点放到“抢在别人前面挖潜在缺陷”。改进 MySQL 时坚持这一点，能从根上托住改动质量；经验表明很有效。条件允许时复制在线流量，是发现隐患、提升整体质量的有力手段。
