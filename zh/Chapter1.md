# 第1章：解决 MySQL 问题的传统方法

## 1.1 解决 MySQL 问题的现状

与“如何使用 MySQL”相关的问题通常并不难：收集信息、做逻辑推理，往往就能解决。真正困难的，是 MySQL 自身的固有问题。好在用户社区很有办法，已经想出了不少对策，例如用线程池缓解可扩展性压力。

要真正解决 MySQL 的深层问题，只在外围打补丁远远不够，必须触及问题本质并系统处理。以组复制为例，其稳定性问题长期存在；尽管投入很大，若方法不对，缺陷仍难明显减少。

## 1.2 MySQL 问题是如何解决的？

下面列举若干经典问题，以及实际场景中的典型应对方式。

如图所示，可扩展性瓶颈明显限制了吞吐量继续上升。例如并发超过 100 后，吞吐量开始回落。正因历史上可扩展性一直是痛点，Percona 甚至开源了线程池。下图是启用 Percona 线程池后，TPC-C 吞吐量与并发度的关系。

<img src="../media/image-20240829080659528.png" alt="image-20240829080659528" style="zoom:150%;" />

图 1-2. Percona 线程池缓解 MySQL 5.7.39 的可扩展性问题。

对 MySQL 5.7.39 而言，线程池能有效抑制吞吐量下滑，但也会带来固有开销，峰值吞吐量略有下降；在低并发对比中，这种开销更明显。

随着 MySQL 8.0 自身可扩展性改善，线程池对“防止吞吐量掉下来”的边际收益也随之变小。后续章节会用实例说明这一点。

### 1.2.3 MySQL 半同步复制在大规模部署中的挑战

自 Paxos 协议流行以来，越来越多数据库用状态机复制构建高可用集群。

Paxos 依赖集合论意义上的多数派达成共识。例如 3 节点集群中，2 个节点即可形成多数；二者达成一致，系统便可继续服务。理论上，坚持多数派规则应能避免异常下的分歧与脑裂。

Raft 同样广为使用，本质上可视为 Paxos 的简化。下文简述 Meta 基于 Raft 实现 MySQL 高可用的方案 [38]，该方案简化了传统高可用流程。

<img src="../media/91bc13de07d658b009ae498b5afa4ac1.gif" style="zoom: 50%;" />

图 1-5. Meta 使用 Raft 的原因。

Meta 的实践表明，基于 Raft 的新方案能简化高可用难题。Raft 常被看作精简版 Paxos；同理，若基于 Paxos 的组复制实现得当，同样可以很优雅。

### 1.2.4 多数派机制的性能及其准确性

在隔离级别为读已提交的条件下，我们对组复制在不同网络延迟下做了模拟。

### 1.2.5 组复制：本机部署仍报告不可达

同一台机器上部署两个组复制节点、经 localhost 通信时，理论上正常情况下不应出现网络抖动、丢包或对端不可达。

日志中可见 “has become unreachable（已变得不可达）” 一类警告。本机场景下如此频繁地报“不可达”，并不合理。把组复制的延迟问题简单归咎于网络，并非上策。后续章节会讨论如何增强网络探测，减少误报。

## 1.3 总结

本章梳理了用户侧常见的 MySQL 问题应对方式。MySQL 8.0 已有明显进步，例如可扩展性改善与哈希连接支持；但老问题与新问题仍大量存在。要有效解决它们，必须把问题本身与相关理论吃透，否则理解难免片面。

下一章通过多个案例说明：某些晦涩的 MySQL 问题极难定位，往往需要广阔知识面与充分的逻辑推理才能找到根因。
